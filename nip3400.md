# Confusing issues with replaceable events:

The following would now be replaceable:

- 3400 escrow/arbiter announce
- 3401 patron task proposal

_NB: older versions of replaceable events aren't **necessarily** discarded. So a relay that wants to provide richer auditability can pledge not to discard old versions._

Possible dispute points:
- 3400 specified a (lower) fee. patron agrees to this fee. work concludes. arbiter replaces their 3400 with a higher fee and disperses lower amount. both the patron and the agent would be aggrieved, but they would only have the most recent 3400 to point to to publicly complain about the arbiter. (partially resolved by NB above)
- what if a patron were to replace their 3401 to change the task status? once the patron has _paid the escrow_, they are now out money and their incentive is to have the task completed (or have some malicious attack worth that amount succeed).
  - they could change it from `assigned` to `concluded` and make the case that the work was actually rejected and they are due a refund (less the arbiter's fee). Their claim would be that the arbiter never actually did their job of publishing the conclusion. This would be a Patron attacking the reputation of an Agent - claiming that their work was bad - and they'd be open to losing the escrow fee in order to do so.
- A similar "attack" could be run by the Agent - they could claim they did the work and submitted it and the Arbiter never published the conclusion.

I think both of these disputes are "resolved" by trusting the arbiter. Once they have the funds, the message is "what the Arbiter says, goes, now. it's always their word against mine".

**Both the Patron paying the Arbiter and the Agent starting work (after confirming with the Arbiter that its a legit task) are signals that "I trust the arbiter absolutely, I relinquish my dispute rights"**

It might be the case that a large set of Patron/Agent teams (or many sock puppets...) could pull off a reputational attack on an Arbiter using combinations of the above, but it would be costly and there are some relay mitigations, like storing histories of replaceable events.

Lightning Network Bounties/Escrow
---------------------------------

`draft` `optional`

This NIP defines event kinds and structure for facilitating Lightning Network escrow services and bounties on nostr. It enables escrow agents to register their services and users to create, accept, and resolve bounty tasks using Lightning Network payments through nostr zaps.

## Events

### Event Kinds

- `3400`: Escrow Agent Registration
- `3401`: Task Proposal
- `3407`: Task Resolution

### Escrow Agent Registration (3400)

_Replaceable_

Used by escrow agents to advertise a given configuration of services. A single escrow agent may advertise many escrow services (say, for different industries, different fee schedules, different dispute policies, etc).

```json
{
  "kind": 3400,
  "content": {
    "name": "<string; title for service (agent name, and/or nickname of service offered, etc.)>",
    "about": "<string (optional); additional details of service>",
    "dispute_resolution_policy_text": "<string (optional); full text of dispute resolution policy>",
    "dispute_resolution_policy_url": "<string (optional); url of dispute resolution policy>",
  },
  "tags": [
    ["p", "<agent-pubkey>", "<optional recommended relay URL>"],
    ["r", "<string (optional); agent details web URL>"],
    ["t", "<optional service category; string>"],
    ["t", "<(additional optional service categories)>"],
    ["flat_fee", "<millisatoshis, stringified>"],
    ["percent_fee", "<decimal 0.0 - 1.0, strinigifed>"],
    ["min_amount", "<optional minimum task bounty this agent will take; integer in sats>"],
    ["max_amount", "<optional maximum task bounty this agent will take; integer in sats>"],
  ]
}
```

**ONE of** `flat_fee` or `percent_fee` is required.

[amount tag ref - NIP 57](https://github.com/nostr-protocol/nips/blob/master/57.md)
[weight tag ref - NIP 57](https://github.com/nostr-protocol/nips/blob/3e8c33ee79e3d2eb46ca498eddadcc6ef1ef7329/57.md)

### Task Proposal (3401)

Used to propose an escrow task with specified terms and requirements.

```json
{
  "kind": 3401,
  "content": {
    "description": "<string>",
    "requirements": "<string>",
    "deadline": "<unix timestamp in seconds>"
  },
  "tags": [
    ["p", "<agent-pubkey>", "<optional recommended relay URL>"],
    ["amount", "<integer in sats>"]
  ]
}
```

### Agent Task Acceptance (3402)

Used by escrow agents to accept task proposals. Only the agent specified in the task proposal can accept it.

```json
{
  "kind": 3402,
  "tags": [
    ["e", "<task-proposal-event-id>", "<optional recommended relay URL>"],
    ["p", "<creator-pubkey>", "<optional recommended relay URL>"]
  ]
}
```

### Task Finalization (3403)

Created after the task creator zaps the agent's acceptance event. This event makes the task live and available for worker applications.

```json
{
  "kind": 3403,
  "content": "",
  "tags": [
    ["e", "<agent-acceptance-event-id>", "<optional recommended relay URL>"],
    ["e", "<zap-receipt-event-id>", "<optional recommended relay URL>"],
    ["p", "<agent-pubkey>", "<optional recommended relay URL>"],
    ["amount", "<integer in sats>"]
  ]
}
```

### Worker Application (3404)

Used by workers to apply for a finalized task.

```json
{
  "kind": 3404,
  "content": "<application details>",
  "tags": [
    ["e", "<task-finalization-event-id>", "<optional recommended relay URL>"],
    ["p", "<creator-pubkey>", "<optional recommended relay URL>"],
    ["p", "<agent-pubkey>", "<optional recommended relay URL>"]
  ]
}
```

### Worker Assignment (3405)

Used by task creator to assign the task to a specific worker.

```json
{
  "kind": 3405,
  "tags": [
    ["e", "<task-finalization-event-id>", "<optional recommended relay URL>"],
    ["e", "<worker-application-event-id>", "<optional recommended relay URL>"],
    ["p", "<worker-pubkey>", "<optional recommended relay URL>"],
    ["p", "<agent-pubkey>", "<optional recommended relay URL>"]
  ]
}
```

### Work Submission (3406)

Used by assigned worker to submit completed work.

```json
{
  "kind": 3406,
  "content": "<work details/proof>",
  "tags": [
    ["e", "<worker-assignment-event-id>", "<optional recommended relay URL>"],
    ["p", "<creator-pubkey>", "<optional recommended relay URL>"],
    ["p", "<agent-pubkey>", "<optional recommended relay URL>"]
  ]
}
```

### Task Resolution (3407)

Used by agent to resolve the task and provide proof of payment.

```json
{
  "kind": 3407,
  "content": {
    "resolution": "completed|rejected|canceled",
    "resolution_details": "<string>"
  },
  "tags": [
    ["e", "<work-submission-event-id>", "<optional recommended relay URL>"],
    ["e", "<zap-receipt-event-id>", "<optional recommended relay URL>"],
    ["p", "<creator-pubkey>", "<optional recommended relay URL>"],
    ["p", "<worker-pubkey>", "<optional recommended relay URL>"],
    ["amount", "<integer in sats>"]
  ]
}
```

## Client Behavior

1. Clients MUST verify all signatures and event relationships before displaying or acting on escrow events
2. Clients MUST verify zap receipts for task finalization and resolution events
3. Clients MUST maintain accurate state of task progression through the event chain
4. Clients SHOULD respect the deadline specified in task creation events
5. Clients MUST NOT consider a task active until finalized with valid zap receipt
6. Clients MUST verify that task acceptance events are signed by the specified agent

## Relay Behavior

1. Relays MAY choose to not store escrow events
2. If a relay stores escrow events, it SHOULD store all related events including referenced zap receipts
3. Relays implementing this NIP SHOULD implement [NIP-01](01.md) replaceable events for agent registration updates

## Security Considerations

1. All events MUST be properly signed by their respective actors
2. Escrow agents MUST verify task completion before releasing funds to worker
3. Escrow agents MUST return funds to creator if task is rejected or canceled
4. Dispute resolution process MUST be clearly defined in agent registration
5. Clients SHOULD verify agent signatures and reputation before engagement
6. Task creators SHOULD verify agent reputation and terms before sending funds
7. Workers SHOULD verify agent reputation before applying to tasks
8. All payment proofs MUST be verifiable through nostr zap receipts
